## Актуальность

Актуальность моей дипломной работы заключается в том, что более 90% автомобилей, продаваемых дилерскими агенствами на Авто.ру, загружаются с помощью XML-фидов. Сервис интеграции данных должен обрабатывать большую нагрузку по обработке изменений объявлений, которая составляет более 2 миллионов автомобилей в сутки

Текущая реализация ненадежна и, как показали учения, при потере инстансов в датацентре теряются фиды из обработки

Оркестрация с использованием системы Temporal набирает огромную популярность среди разработчиков

---

## Сравнение оркестраторов

Для нового сервиса я рассмотрел три различных оркестратора: Apache airflow, Camunda и Temporal.

Apache Airflow отлично подходит для коротких задач, но не для долгих процессов и основной язык не подходит под требуемый стек. 
Camunda хороша для бизнес-процессов с визуальным моделированием, но уступает системе Temporal в простоте реализации бизнес-процесса

Temporal позволяет описывать бизнес процесс кодом, имеет Java SDK и является более актуальным решением по сравнению с Camunda. Именно
поэтому он был выбран как платформа оркестрации.

## Бизнес процесс

Основной бизнес-процесс которым занимается сервис интеграции - обработка поступающих от дилера XML файлов с 
описание автомобилей, называемых фидами

Бизнес-процесс состоит из набора шагов:
1) Загрузка XML файла с сервера и парсинг
2) Загрузка изображений автомобиля на внутренние сервера
3) Конвертация адреса автосалона в координаты
4) Сопоставление комплектации автомобиля и его опций
5) Отправка готового объявления на внутренний сервис для последующей выкладки

## Бизнес процесс в Temporal

После того как я составил схему основного бизнес-процесса по старому сервису 
я приступил к трансляции этой последовательности шагов на систему Temporal

У меня получилась 3-х уровневая архитектура состоящая из трех видов воркфлоу:
ScheduleWorkflow, FeedWorkflow для уровня фида и OfferWorkflow для уровня обработки автомобиля

ScheduleWorkflow запускается каждые 10 секунд, получает из базы данных новые фиды, поступающие в обработку и для каждого фида запускает новый FeedWorkflow

FeedWorkflow в свою очередь загружает фид и парсит его. Далее для каждого автомобильного объявления из фида запускает дочерний OfferWorkflow

OfferWorkflow занимается обработкой автомобиля - конвертирует адрес, комплектацию автомобиля и загружает изображения. Далее отправляет сконвертированное объявление обратно в FeedWorkflow для последующей отправки в очередь сообщений

## Особенность Temporal

При разработке архитектуры я столкнулся со сложностью - ограничения размера 
истории воркфлоу в системе Temporal.

В temporal есть ограничение на 50 тысяч событий внутри одного бизнес-процесса. Фид с описанием автомобилей может содержать до 5000 автомобилей, что в первой реализации архитектуры бы привело к переполнению истории

Чтобы избежать данной проблемы я использовал функцию Continue-As-New. Она 
позволяет запустить новый бизнес-процесс из старого, "как-бы" продолжая исполнение

Для ее применения я модифицировал архитектуру - теперь FeedWorkflow обрабатывает только первые 100 автомобилей, а далее обработка переходит в новый воркфлоу

## Ключевые технические решения

Для того чтобы достичь поставленной цели по повышению отказоустойчивости я 
разработал ряд технических решений

1) Использование оркестратора Temporal

Использование оркестратора позволяет размыть статическое распределение 
бизнес-процесса по инстансам приложения. Теперь бизнес-процесс равномерно и 
бесшовно распределяется между всеми инстансами, и частичный выход из строя
одного экземляра приложения не приводит к каким-либо изменениям в архитектуре

Так же отказ от библиотеки akka-streams решил проблему с утечками памяти, возникающими из-за дефектов библиотеки

1) Использование кеша 

Для нового сервиса я создал внешний кеш в виде таблиц в базе данных YDB.
Внешнее хранилище позволяет уменьшить среднее время до восстановления и снижает нагрузку на внешние сервисы во время релизов

## Сравнение

Система протестирована на трёх уровнях: unit-тестирование, интеграционные тесты и тесты сравнения 
со старым сервисом для проверки сохранения функциональных требований обработки фида

По итогам шести месяцев в боевом окружении были получены следующие результаты: 
1) Время непрерывной работы выросло с 60 до 180 дней что дало прирост в 300%
2) Медианное время восстановления после сбоя сократилось с 15 минут до 15 секунд что дало прирост 98%
